# Spec: OpenAI-generated inquiry drafts

## Why

The Convex All Gas judging criteria score the sponsor stack on this basis:

> OpenAI, Firecrawl, and AgentMail do real work in your product. They generate,
> crawl, or send, not just sit in the README.

Today the app satisfies two of three:

- **Firecrawl — crawls.** `convex/discovery.ts` searches and scrapes real
  property pages. Real work.
- **AgentMail — sends.** `convex/inquiries.ts` creates a per-user inbox and
  sends the inquiry. Real work.
- **OpenAI — nothing.** There is no `openai` dependency in `package.json`, and
  no line in `src/` or `convex/` that contacts an OpenAI endpoint.

Using Codex to *write* this codebase does not satisfy the criterion. The
criterion is about the running product: when a user clicks "Follow up" on the
live site, an OpenAI API call must happen. Right now the inquiry email is built
by a client-side template literal at `src/Dashboard.tsx:95` — pure string
concatenation, no model involved.

`hackathon.md:13` currently states "**AI models:** none", which advertises the
gap to judges.

## Goal

The inquiry draft is generated by an OpenAI model, server-side, in a Convex
action — with the existing template kept as a fallback so the demo cannot break.

This is the right place for the model because it is the one step in the product
where prose must be *written*, it sits in the demo's critical path (so it is
visible in the video), and it reinforces the app's existing thesis: the draft
should ask the leasing office about exactly the details the listing failed to
confirm.

## Non-goals

- Do not use a model anywhere in discovery, extraction, or filtering.
  `convex/discovery.ts` already uses Firecrawl's structured extraction and works.
  Changing it risks the whole demo.
- Do not auto-send. The user reviews and edits before sending. Keep that.
- Do not remove or rewrite the existing template. It becomes the fallback.

## Task 1 — Server-side draft generation

### 1.1 Environment

Add `OPENAI_API_KEY` to the Convex deployment environment settings
(`affable-chipmunk-297`), alongside the existing `FIRECRAWL_API_KEY` and
`AGENTMAIL_API_KEY`.

Never prefix it `VITE_` — that would expose the key to the browser.

### 1.2 New file: `convex/drafts.ts`

Call the OpenAI REST API with plain `fetch`. Do not add the `openai` npm
package: `fetch` works in Convex's default action runtime, adds no dependency,
and avoids any interaction with the existing `patch-package` postinstall step.
Deadline is tight; this path has the fewest ways to fail.

Two exports:

**a. `draftContext` — an `internalQuery`.**

Mirror the ownership pattern already used by `threadAccess` in
`convex/inquiries.ts`:

- `requireUser(ctx)` (from `./users`)
- Load the listing, then its search
- Throw `ConvexError("Listing not found.")` if the listing is missing or
  `search.userId !== user._id`
- Return the fields the prompt needs: `title`, `complexName`, `url`, `rent`,
  `bedrooms`, `summary`, `matches`, `unknowns`, plus the search's `preferences`

Ownership must be enforced here, not in the action. An action cannot read the
database directly, and an unauthenticated caller must not be able to spend
OpenAI credits on an arbitrary listing id.

**b. `compose` — a public `action`.**

Signature: `args: { listingId: v.id("listings") }`, returns
`{ subject: string; body: string }`.

Follow the shape of the existing public action `inquiries.replies` — it already
demonstrates a browser-callable action that delegates auth to an internalQuery.

Behavior:

1. `ctx.runQuery(internal.drafts.draftContext, args)`
2. Derive the unconfirmed details the same way the current UI does — filter
   `listing.unknowns` for entries ending in `" not confirmed"` and strip that
   suffix. This list is the core of the prompt.
3. POST to `https://api.openai.com/v1/chat/completions` with
   `Authorization: Bearer ${process.env.OPENAI_API_KEY}`.
4. Use a JSON response format and parse `{ subject, body }` out of it.
5. **Clamp before returning.** `convex/inquiries.ts:18` rejects a subject over
   200 chars, a subject containing `\r` or `\n`, an empty subject or body, and a
   body over 5000 chars. Strip newlines from the subject, trim, and slice both.
   If generated output violates these after clamping, throw — the client falls
   back to the template.
6. Wrap the whole call in try/catch. On any failure, log server-side with
   `console.error` (matching the style in `inquiries.prepare`) and throw a
   generic error. Do not leak the API error text to the browser.
7. Add a timeout — `AbortController` at about 15 seconds. A hung request must
   not leave the modal spinning during a demo.

### 1.3 Prompt

The system prompt should produce a short, specific, plain email from a
prospective renter. Requirements to encode:

- Address the listing by `title` and `complexName` where present.
- State the renter's budget range, bedroom count, move-in timing, pets, and
  requested amenities — these come from `preferences`.
- **Ask explicitly about each unconfirmed detail**, by name. This is the point of
  the feature: the listing page did not confirm these, so the email chases them.
- Ask to confirm availability, total monthly cost, lease terms, and how to
  schedule a tour.
- No marketing language, no emoji, no invented facts about the apartment. The
  model may only use the fields it is given.
- Sign off without inventing a name — the user edits before sending.

Keep `temperature` low (0.3 or so). This is a business email, not a creative
task.

### 1.4 Frontend: `src/Dashboard.tsx`, `InquiryForm`

Current state: `draft` is computed synchronously at line 95 and passed to the
textarea via `defaultValue`.

Changes:

1. Keep the existing template expression exactly as it is. Rename it to
   `fallbackDraft`.
2. Add `const compose = useAction(api.drafts.compose);` — `useAction` is already
   imported and used in `Conversations`.
3. Add state: `const [draft, setDraft] = useState<string | null>(null)` and a
   `drafting` boolean.
4. In a `useEffect` on mount, call `compose({ listingId: listing._id })`. On
   success set the subject and body from the result. On failure set
   `fallbackDraft` and the existing default subject. Either way, clear
   `drafting`.
5. While `drafting`, disable the textarea and the send button, and show a status
   line — "Drafting your message…" with `role="status"`, matching the existing
   loading-state style (`<p role="status">Loading conversations…</p>`).

**Implementation gotcha — this will silently not work otherwise:** the textarea
and subject input currently use `defaultValue`, which React only reads on first
mount. Setting draft state later will not update an uncontrolled field. Convert
both fields to controlled inputs with `value` + `onChange`, or remount the form
with a `key` that changes when the draft arrives. Controlled is cleaner; the
`submit` handler can then read from state instead of `FormData`.

Do not block the modal from opening on the API call. The modal opens, then fills.

### 1.5 Health check

Extend `convex/services.ts` with an `internalAction` named `checkOpenai`,
matching the existing `checkAgentmail` shape — a cheap read-only call that
returns `{ connected: boolean }` and swallows the error into a field. Useful for
verifying the key is set before the demo without sending anything.

### 1.6 Tests

Add `tests/drafts.test.ts` following the existing vitest + `convex-test`
patterns in `tests/`. Stub `globalThis.fetch`. Cover:

- Ownership: another user's `listingId` throws.
- A well-formed model response returns `{ subject, body }`.
- An over-long body is clamped to 5000 chars; a subject with a newline is
  cleaned and clamped to 200.
- A failed fetch throws rather than returning malformed output.

All 119 existing tests must still pass.

2. `npm test` — 119 existing tests pass, plus the new draft tests.
3. `npm run build`, then `npm run deploy`.
4. On the live site in a private window: create an account, run a search with a
